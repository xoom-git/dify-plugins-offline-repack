## 1. 关键事实（调研结论，全部可复核）

### 1.1 difypkg 就是 zip，包根 = 插件源码目录

- 官方 daemon 解码器把 `.difypkg` 当作 zip 打开；文件直接平铺（`main.py`、`manifest.yaml`、`provider/`、`tools/`…在 zip 根），解压到插件工作目录即插件源码。
  - 代码：`pkg/plugin_packager/decoder/zip.go`（`ExtractTo` 平铺解压、路径穿越防护、解压总大小限制）、`internal/core/local_runtime/environment.go`（解压到 `WorkingPath`）。
- 签名：zip 注释里是 `{"signature": "...", "time": ...}`（RSA PKCS1v15/SHA256，langgenius 公钥内置）；另可选 `.verification.dify.json`。带签名样例见工作区 `web_001/webscraper.signed.difypkg`（仅比未签名多一个该文件）。
- 结论：**没有官方的“依赖目录”概念**；要离线，只能让“环境初始化阶段”本身离线完成（见 1.3）。

### 1.2 安装 = 建 venv + 联网装依赖

plugin_daemon 对本地 Python 插件（Dify 1.16/1.17，daemon 0.6.10-local）执行：

1. 解压 difypkg 到 `/app/storage/cwd/<plugin>/`；
2. `uv venv .venv --python 3.12`；
3. 依赖文件探测（`detectDependencyFileType`）：
   - 存在 `pyproject.toml` → `uv sync --no-dev [--frozen]`（有 `uv.lock` 且未设 `PLUGIN_IGNORE_UV_LOCK`）；
   - 否则 `requirements.txt` → `uv pip install [-i PIP_MIRROR_URL] -r requirements.txt`；
   - 都没有 → 报错 `neither pyproject.toml nor requirements.txt found`。
4. `compileall` 预编译、`import dify_plugin` 预加载；
5. 写 `.venv/dify/plugin.json`（venv 有效标记）。

- 探测优先级细节：若配置了 `PIP_MIRROR_URL`，**优先 requirements.txt**（避免 uv lock 的索引 URL 与镜像不匹配）。
- 时间/网络：安装全程 10 分钟上限；无输出 120 秒（`PYTHON_ENV_INIT_TIMEOUT`）即被杀。**零外网且无镜像时必然失败**——这是问题根因。
  - 代码：`internal/core/local_runtime/environment_python.go`、`setup_python_environment.go`、`internal/core/local_runtime/dependency_installation_test.go`。

### 1.3 可被 daemon 识别的“离线钩子”（本方案核心依据）

daemon 使用 uv/pip 从包内依赖文件安装，而 **uv 与 pip 都支持把本地 wheel 目录作为唯一源**：

| 依赖文件形态 | daemon 执行 | 离线注入方式 |
|---|---|---|
| 仅 `requirements.txt` | `uv pip install -r requirements.txt` | 首行注入 `--no-index --find-links=./wheels/`，并把锁定 wheel 全集放 `wheels/` |
| 有 `pyproject.toml`（uv 项目） | `uv sync`（读项目配置） | 向 `pyproject.toml` 注入 `[tool.uv]`：`no-index = true`、`find-links = ["./wheels"]`；wheel 全集放 `wheels/` |

- 相对路径 `./wheels/` 以 daemon 执行时工作目录（插件源码根）为基准，成立。
- uv 会按 **PEP425 兼容标签**从 find-links 目录挑取匹配 wheel；因此把 amd64 与 aarch64（cp312-manylinux_2_17_*）wheel **同时放入同一 `wheels/`**，不同架构目标会各自选对——**单包双架构可行**。
- 必须与目标 daemon 的 python 一致：`uv venv --python 3.12`（0.6.10 硬编码 3.12；镜像基础为 python 3.12 系）。

### 1.4 已知“半成品离线包”翻车点（issue #25356 教训）

`yfinance`（依赖 `peewee`）在 `--only-binary=:all:`/无 wheel 场景解析失败 → “wheel was not found in the provided package locations”。启示：
- 依赖解析必须**精确锁定**（离线时不再解析），且对 **sdist-only 依赖要预构建出 wheel**（在有网容器内 `pip wheel`/uv build 到目标 python/架构），或明确失败；
- 不能只下载部分 wheel 假装离线包。

### 1.5 目标端限制与配置面（daemon 侧事实）

- `MAX_PLUGIN_PACKAGE_SIZE`（compose 默认 `52428800`，约 50MB）：既限**上传体**也限**解压后总量**（`ZipDecoderWithSizeLimit` 累计 UncompressedSize）。
- `FORCE_VERIFYING_SIGNATURE` 默认 **true**：任何不能被内置 langgenius 公钥或 `THIRD_PARTY_SIGNATURE_VERIFICATION_PUBLIC_KEYS`（逗号分隔容器内路径，启用需 `THIRD_PARTY_SIGNATURE_VERIFICATION_ENABLED=true`）验签的包在 upload 阶段被拒。
  - 代码：`internal/service/plugin_decoder.go`（`UploadPluginPkg`）、`internal/types/app/config.go`。
- `PIP_MIRROR_URL`/`PIP_EXTRA_ARGS`/`PIP_MIRROR_AUTO_DETECT` 等仅属“镜像/参数”配置面，非本工具依赖项。
- 前端 Nginx 上传体限制 `NGINX_CLIENT_MAX_BODY_SIZE`。
- 上述变量均在 Dify `.env`，改后需重建相应容器（`docker compose up -d`）。

### 1.6 官方 CLI 与参考实现

- plugin_daemon 每个 release 发布 4/8 个平台二进制：`dify-plugin-{darwin,linux,windows}-{amd64,arm64}`（0.6.10 与目标 daemon 同版本）——内含 `plugin package`/`signature` 等命令，可做“与官方一致的最终打包/签名”。
- 参考实现 [junjiem/dify-plugin-repackaging](https://github.com/junjiem/dify-plugin-repackaging)：Shell + python3.12-slim + 官方 CLI；先例验证了“wheels + 改写依赖文件 + 重新打包”路线可落地（它要求目标端 `FORCE_VERIFYING_SIGNATURE=false`、放大包限制），但存在 §01-1.3 的工程化短板（本方案在 FR-2/3/4/7 上系统性解决）。

## 2. 方案选型

### 2.1 离线化路线对比

| 路线 | 描述 | 评价 |
|---|---|---|
| A. 内置完整 `.venv` 快照 | 打包含建好的 venv，daemon 校验到有效 `.venv/dify/plugin.json` 即跳过安装 | 受 daemon 内 python 绝对路径/symlink/镜像差异影响大，包体巨大，跨 daemon 版本脆弱 → 不选为主 |
| **B. wheel 闭包 + 依赖文件离线化（本方案）** | 注入 `wheels/` 全集 + `requirements.txt` 首行/`[tool.uv]` 离线配置；依赖**精确锁定** | 与 uv/pip 官方语义一致、双架构单包可行、包体可控、跨 daemon 兼容面宽 → **采用** |
| C. 目标端配内网 PyPI 镜像 | `.env` 设 `PIP_MIRROR_URL` | 需内网 pip 源；不满足纯离线；作为文档备选提及 |

### 2.2 目标 python/架构

- python **3.12**（daemon 0.6.10 `uv venv --python 3.12`）；
- 架构 **amd64 + arm64 双 wheel 集单包**（PEP425 自动选择），可退化单架构；
- wheel 平台标签以 manylinux_2_17/2014 覆盖现代 daemon 基础镜像。

### 2.3 工具形态

- **Docker 优先 CLI**（评审已定）：主命令在宿主机执行，实际构建编排进 `python:3.12`（或由官方 daemon 镜像派生的构建镜像）容器；容器内：
  - 用 **uv**（锁定、下载/构建 wheel、跨平台解析），
  - 用官方 `dify-plugin-linux-*` CLI（可选）做规范打包/签名；
- 全部产物与报告经挂载目录回写宿主机；供应链 sha256 入报告。

### 2.4 目标端两种安全策略（FR-8）

| | 快速路径（兜底） | 安全路径（推荐默认交付） |
|---|---|---|
| 目标端改动 | `.env`: `FORCE_VERIFYING_SIGNATURE=false` | 挂载组织公钥 + `.env`: `THIRD_PARTY_SIGNATURE_VERIFICATION_ENABLED=true`, `THIRD_PARTY_SIGNATURE_VERIFICATION_PUBLIC_KEYS=<容器内路径>` |
| 产物 | 未签名离线包 | 工具自签离线包（RSA，zip 注释 + `.verification.dify.json`） |
| 风险 | 任何未上架插件均可装 | 仅持有我方私钥的包可装 |

两条路径都需按需放大 `PLUGIN_MAX_PACKAGE_SIZE` 与 `NGINX_CLIENT_MAX_BODY_SIZE`（文档给出）。

## 3. 总体架构

```
宿主（Windows/macOS/Linux）              Docker 构建容器（python:3.12 + uv + 官方 CLI）
┌───────────────────────┐               ┌──────────────────────────────────────────┐
│ dify-offline-repack   │  docker run   │ 1 inspect/解析 difypkg                    │
│  · inspect/repack/…   │ ─────────────▶ │ 2 依赖锁定 (uv lock/export, 目标平台)     │
│  · batch/verify/keygen│  挂载 volume   │ 3 wheel 获取 (uv/pip download/构建, 双架构)│
│  · 产物+report+部署说明│ ◀───────────── │ 4 包内改造 (wheels/ + 依赖文件离线化)     │
└───────────────────────┘               │ 5 官方 CLI 规范打包/可选自签               │
                                        │ 6 静态校验(report.json/summary)            │
                                        └──────────────────────────────────────────┘
   目标端（零外网 Dify 1.16/1.17）：
   上传 offline.difypkg → daemon 解压 → uv 仅从 ./wheels 解析 → 安装成功
```

- 中间产物目录（每插件）：`work/<plugin>/`（改造后源码 + wheels）、`out/<plugin>-offline-<version>.difypkg`、`report/<plugin>.json`。
- 幂等与缓存：以“源包 sha256 + 参数”为键缓存下载 wheel（P2）。

## 4. 关键设计决策与理由

| # | 决策 | 理由 |
|---|---|---|
| D1 | requirements 首行 `--no-index --find-links=./wheels/`；pyproject 注入 `[tool.uv]` | 直接命中 daemon 两条安装路径（1.3），且旧版 pip 流程对首行同样识别 |
| D2 | 锁定用 uv（同一解析器贯穿锁定/下载） | 避免 pip 与 uv 解析不一致（R3） |
| D3 | 未找到目标 wheel 时**构建**而非跳过；仍失败则硬报错 | 杜绝“半成品离线包”（#25356 教训） |
| D4 | wheel 放源码根 `wheels/`，不改动业务文件 | uv/pip 相对路径基准成立；diff 可审计 |
| D5 | 默认双架构单包 | 简化内网分发；uv/pip 按 tag 自动选择 |
| D6 | 官方 CLI 做最终打包（镜像内置 linux 二进制），可选 `signature` 自签 | 包结构与官方一致，避免自研 zip 细节偏差；产物可进“安全路径” |
| D7 | 静态校验（离线复现采用 `uv sync/install --offline` 语义自检）内置 | FR-7 无网即可快速回归，不必每次都起全套 daemon |
| D8 | 目标端零改代码，仅 .env/挂载配置 | NGO-1 |

## 6.1 实测补充（2026 调研期，详见《03-验证记录.md》）

机制已验证：① requirements 首行 `--no-index --find-links=./wheels/` 在 uv 0.12.9 与 pip 上均离线可用（旧 uv 0.5.9 相对路径缺陷已修复）；② pyproject 注入 `[tool.uv] {no-index=true, find-links=["./wheels"]}` 后 `uv sync --offline` 可用；③ webscraper 官方依赖在 linux/cp312 下锁定为 **46 包**（dify-plugin 0.9.1 SDK 自带 flask/gevent/httpx/pydantic/tiktoken/yarl 等闭包）。

对实现新增的三条硬约束：

| # | 约束 | 对策（落入设计） |
|---|---|---|
| C1 | uv 锁定不校验 wheel 可用性；wheel 平台地板须匹配目标 glibc。实测 `gevent==26.8.0` 仅提供 manylinux_2_28 wheel，用 manylinux2014(2_17) 地板获取必然失败 | 提供 `--manylinux-floor`（默认 **2_28**，对应 python:3.12-slim/bookworm glibc 2.36）；锁定后必须做“本地目录离线重解析”自检（FR-7） |
| C2 | pip 跨平台下载按运行机求值 `sys_platform` 等 marker（实测 Windows 上取 linux wheel 时要求 win32 cffi）→ 不可用于异 OS 获取 | 解析+获取一律用 uv `--python-platform/--python-version`，并在 **Linux 构建容器**内执行（Docker-first 的正确性理由）；Windows 仅编排 |
| C3 | uv 无系统 3.12 时自动下载托管 CPython 3.12（实测 3.12.8），与 daemon `uv venv --python 3.12` 同语义 | 锁定标签固定 cp312；无需依赖镜像内 python 路径 |

**本机环境限制**：Docker Hub 当前不可达（无代理）→ “真 plugin_daemon 容器离线 e2e”（PRD T1/T10）需打通镜像源后在 CI/有网机器执行；工具将自带 `e2e/` 脚本供任意有网环境一键跑。
