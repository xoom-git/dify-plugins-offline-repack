## 2. 核心机制验证

### V1：requirements.txt 首行 `--no-index --find-links=<本地目录>` 离线安装
- 样例：`deps/idna-3.10-py3-none-any.whl` + 首行 `--no-index --find-links=./deps` + `idna==3.10`。
- uv 0.5.9：**失败**（`Invalid URL ... relative URL without a base`——旧版不接受相对路径）。
- **uv 0.12.9：成功（EXIT 0，离线完成安装）** —— 相对路径缺陷已被修复；daemon 安装最新 uv，故首行相对 `./wheels/` 可用。
- pip 26.1.2：成功（EXIT 0），兼容旧版 pip 流程。
- **结论：requirements-only 插件的离线钩子成立（现代 uv 与 pip 均识别该首行）。**

### V2：pyproject.toml 注入 `[tool.uv]` 离线配置后 `uv sync`
- 样例 pyproject：`[project]` 依赖 `idna==3.10`；`[tool.uv] {no-index=true, find-links=["deps"], package=false}`；`deps/` 内含 idna wheel。
- `uv sync --offline`：**成功（EXIT 0）**；`.venv` 内 `import idna` OK。
- **结论：pyproject 插件的离线钩子成立**（daemon `uv sync` 读取 `[tool.uv]`；相对路径以项目目录为基准）。

### V3：真实官方插件（webscraper）依赖闭包锁定
- 输入：`web_001/webscraper/requirements.txt`（dify_plugin>=0.9,<0.10 / beautifulsoup4>=4.12 / lxml>=5.0）。
- `uv pip compile --python-version 3.12 --python-platform linux`：**成功**，锁定 **46 个包**：
  - dify-plugin **0.9.1**（SDK 自带闭包：flask、gevent 26.8.0、httpx、pydantic、tiktoken、yarl、requests 等）、beautifulsoup4 4.15.0、lxml 6.1.3、soupsieve、typing-extensions…（完整清单见 `.research/spike-uvreq/wsc/webscraper-lock.txt`）。
- 含义：离线包需携带的闭包规模约为 **40–60 wheel/十~数十 MB**（模型类重依赖插件会更大）；包体与解压尺寸受目标端 `PLUGIN_MAX_PACKAGE_SIZE` 约束（默认 50MB）。

## 3. 平台语义约束（对工具实现最重要，已并入方案与风险）

### C1：锁定（uv）不看 wheel 可用性，且 wheel 的 manylinux 地板必须匹配目标 glibc
- 事实：uv 锁到 `gevent==26.8.0`；但其 cp312 wheel 只提供 **manylinux_2_28** 标签；以 `--platform manylinux2014_x86_64`（glibc 2.17 地板）下载时 pip 报“无匹配版本（最高 25.9.1）”——**不是缓存，是平台过滤**。
- 处置：wheel 平台地板按目标 daemon 镜像 glibc 选择（python:3.12-slim/bookworm = glibc 2.36 → **manylinux_2_28 地板**）；或直接在目标同源 Linux 容器内原生解析+获取，消除地板猜测。工具需提供 `--manylinux-floor`（默认 2_28）并可调。

### C2：pip 跨平台下载按“运行机”求值 sys_platform 等 marker
- 事实：Windows 上为 linux 目标 `pip download gevent` 解析出 `cffi...; sys_platform == "win32"` 分支并失败 → **pip download 不可用于异 OS 目标获取**。
- 处置：解析与获取一律使用 **uv 的 `--python-platform/--python-version`**（marker 按目标求值），且获取在 **Linux 构建容器**内执行（Docker-first 的又一个正确性理由）；Windows 仅做编排与产物回写。

### C3：uv 会自管 CPython 3.12
- 事实：本机无 python3.12 时 `uv venv/sync` 自动下载托管 CPython 3.12.8。
- 含义：daemon 0.6.10 `uv venv --python 3.12` 用同语义 python，产物锁定 cp312 即可（无需关心镜像自带 python 路径差异）。

### V7 签名（安全路径）—— 已通过官方二进制双向交叉验证 ✅
- 引擎已实现 `keygen/sign/signverify`（RSA-4096 PKCS1v15/SHA256），算法逐行对齐 daemon 0.6.10 tag 源码（tag 与 main 的 `signer/withkey/sign_with_key.go`、`decoder/verifier.go`、`utils/encryption/rsa.go` 逐字节相同）。
- **关键排障**：Python `cryptography` 的 `sign/verify(data, PKCS1v15(), hashes.SHA256())` 会**对入参再次哈希**，而 Go `rsa.SignPKCS1v15(key, SHA256, digest)` 签的是**预哈希摘要** → 早期实现双重哈希导致互验失败；改用 `utils.Prehashed(hashes.SHA256())` 后全部通过。期间借助 Go 1.26 工具链 + daemon 官方包探针（`.research/sigtest/goprobe`，Go 侧逐文件 sha 与 Python 一致）定位确认。

### V14 cp312 守卫与 2026 生态兼容（矩阵扩至 7 个官方插件）
- **问题**：2026+ 大量 Rust/C++ 依赖（tokenizers 0.22、safetensors 0.7 等）最新版**停发 cp312 wheel**（转 cp313/`cp314t`）；daemon 运行时固定 cp312。
- **对策（已实现并验证）**：
  1. 锁定后**逐 pin 审计 cp312 wheel 可用性**；缺失时用 uv 约束文件**自动降钉**至仍发 cp312 轮子的最新版本（`tokenizers==0.20.3` 级别），迭代收敛；
  2. 支持 **abi3** 轮子（`cp310-abi3-*` 等，对 3.12 有效；修复 `cp310` 数字解析为 minor）；
  3. 支持 **`py2.py3-none-any`** 通用标签；
  4. 真正“从未发 cp312 轮子”的依赖给出明确失败与原因（无半成品包）。
- **结果**：新增 4 个官方插件批量重打包全过 —— tavily(0.1.11, tool)、serper(0.0.8, tool)、duckduckgo(0.0.11, tool, 22.4MB, 含 abi3 的 primp)、jina(0.0.23, model, 48.9MB)。
- **真容器抽查**：duckduckgo 离线包在 plugin_daemon 镜像 `--network none` 下 `IMPORT-OK dify_plugin / primp`（abi3 轮子在 3.12 可装可导）。

### V16 单架构（arm64）假失败修复（用户实测反馈驱动）
- 现象：langgenius/openai 1.0.4 选“仅 arm64”在旧引擎下报 `offline recheck failed`（已产出包但判失败）。
- 根因：wheel 全为 aarch64+any，而离线闭包自检默认以 **x86_64 linux** 目标编译 → 判定“无可用 wheel”。
- 修复：`offline_recheck` 支持 **架构三元组**（`aarch64-unknown-linux-gnu` / `x86_64-unknown-linux-gnu`），引擎按每个请求架构分别自检（report 记录 `offline recheck[arch]=ok/FAIL`，全部通过才算成功）。
- 验证：用户文件（与市场包 sha 一致）在修复后 **x86_64 / aarch64 / 双架构三种配置全部 ok=True**；Web 页面（宿主 :8010 与重建的容器 :8011）aarch64 用例 done/recheck True、下载 13,079,346 字节。

### V17 sdist-only 依赖引擎集成（odfpy 场景，V12 机制的落地）
