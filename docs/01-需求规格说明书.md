## 1. 项目背景与问题定义

### 1.1 场景描述

- 目标单位在内网（局域网）**离线部署 Dify 1.x（Docker Compose 形态，本期以 1.16+/1.17 为主）**，服务器不连外网。
- 运维/实施人员从可联网机器下载 Dify 官方插件（`.difypkg`，例如 Marketplace 的 webscraper / agent / 各类工具与模型插件），拷贝到内网后，在 Dify **插件 → 从本地文件安装** 上传。
- 结果：**安装失败**，典型错误：
  - `init environment for plugin xxx failed too many times ... package is corrupted or your network is unstable`
  - `failed to install dependencies ...` / `init process exited due to no activity for 120 seconds`
  - uv/pip 报无法解析依赖（`No solution found when resolving ... wheel was not found in the provided package locations`）

### 1.2 问题根因（实证）

Dify 的插件安装由 `plugin_daemon`（Go 服务，Docker 镜像 `langgenius/dify-plugin-daemon:0.6.10-local`，与 Dify 1.16/1.17 相同）完成。安装时 daemon 会把 `.difypkg` 解压到插件工作目录，然后**在线创建 Python 虚拟环境并解析安装插件声明的依赖**：

1. 用 `uv venv .venv --python 3.12` 建虚拟环境；
2. 若插件含 `pyproject.toml` → `uv sync --no-dev [--frozen]`；
3. 否则按 `requirements.txt` → `uv pip install [-i PIP_MIRROR_URL] -r requirements.txt`；
4. 之后 `compileall` 预编译、写 `.venv/dify/plugin.json` 有效性标记。

默认 `PIP_MIRROR_URL` 为空、无镜像可回退时 uv/pip 访问公网 PyPI；**目标机无外网 → 依赖安装必然失败**（`PYTHON_ENV_INIT_TIMEOUT` 默认 120 秒无活动即被杀）。

> 证据：
> - daemon 源码：`internal/core/control_panel/launcher_local.go`（init environment）、`internal/core/local_runtime/environment_python.go`、`setup_python_environment.go`、`internal/types/app/config.go`（`PIP_MIRROR_URL`/`FORCE_VERIFYING_SIGNATURE`/`MAX_PLUGIN_PACKAGE_SIZE` 等）。
> - 真实案例：[dify#25356（2.0.0-beta 离线安装失败，uv 解析 peewee 缺 wheel）](https://github.com/langgenius/dify/issues/25356)、[dify discussion#30725（1.9.2 离线环境 init environment 失败）](https://github.com/langgenius/dify/discussions/30725)、[discussion#25606（本地安装报错）](https://github.com/langgenius/dify/discussions/25606)、[Dify 社区：离线安装插件流程求助](https://forum.dify.ai/t/topic/1436)。

**结论**：失败点不是 `.difypkg` 本身损坏，而是**包内没有携带运行时 Python 依赖，安装期需要联网下载**。因此“把依赖完整打进球体包、让安装阶段零联网”是正确解法，与本项目目标一致。

### 1.3 现状与不足

| 现有做法 | 说明 | 不足 |
|---|---|---|
| 手工打包（论坛/博客教程） | 在有网环境先让 daemon 装一次，再把含 `.venv` 的工作目录打成包 | 依赖 daemon 具体镜像/路径，脆弱、不可批量、易因 venv 内绝对路径/symlink 失效；python/架构不匹配即失败 |
| [junjiem/dify-plugin-repackaging](https://github.com/junjiem/dify-plugin-repackaging)（社区参考实现） | Shell 脚本 + Docker(python3.12-slim) + 官方 `dify-plugin-<os>-<arch>` CLI；下载市场包→下载 wheels 到 `./wheels/`→改写 `requirements.txt`/注入 `[tool.uv]`→重打包 | 单机脚本工程化弱：`--only-binary=:all:` 对无 wheel 的 sdist 依赖直接失败（正是 25356 的场景）；无精确锁定、无闭包自检、无批量清单、无双架构同包策略、无测试 |
| 配置内网 PyPI 镜像 | 目标端 `.env` 设 `PIP_MIRROR_URL` | 需要内网额外部署/开通 PyPI 源，且不满足“完全离线”前提；dify 1.x 无网络时仍可能被自动探测拖慢 |

本项目在此基础上，交付**工程化的通用离线重打包 CLI 工具**。

### 1.4 术语表

| 术语 | 含义 |
|---|---|
| difypkg | Dify 插件包文件（zip 容器，内容为插件源码 + manifest.yaml；签名置于 zip 注释与 `.verification.dify.json`） |
| plugin_daemon | Dify 的插件守护进程（Go），负责插件安装、环境初始化、进程生命周期 |
| 工作目录 / WorkingPath | daemon 解压插件源码并建 venv 的目录（默认 `/app/storage/cwd/<plugin>/`） |
| uv | Python 包管理/环境工具，daemon 环境初始化用 uv 创建 venv 与安装依赖 |
| wheel | Python 预构建分发包（文件名含 cp312/manylinux_2_17_x86_64 等兼容标签） |
| 离线包（offline difypkg） | 经本工具重打包、内含全部依赖 wheel 的 `.difypkg`，可在零外网目标端安装 |

## 2. 目标与非目标

### 2.1 项目目标（GO）

- **GO-1**：提供“**Docker 优先的通用命令行重打包工具**”，输入官方（或第三方）插件本地 `.difypkg`/插件源码目录，输出**可在完全离线 Dify 上本地文件安装**的 `.difypkg`。
- **GO-2**：包内完整携带 Python 依赖（wheel 全集 + 精确锁定清单），使安装期**零联网**、不依赖目标端任何 pip 源/镜像配置。
- **GO-3**：一次构建产物同时适配 **Linux amd64 与 arm64**（python 3.12，与目标 plugin_daemon 一致）；必要时可退化为按架构输出。
- **GO-4**：内置**校验**（依赖闭包完整性、产物结构、可选离线试装验证）与**清晰中文诊断**，输出“产物 + 报告 + 目标端部署说明”。
- **GO-5**：工程化交付：CLI 幂等、批量模式、可进 CI（GitHub Actions/内部流水线）、完整文档与验收样例。

### 2.2 非目标（本期明确不做）

- **NGO-1**：不修改 Dify / plugin_daemon / dify 本体代码，不做“魔改版 Dify”分发（仅目标端 `.env` 必要项配置说明）。
- **NGO-2**：不自建内网 PyPI/包镜像（那是镜像方案，非本工具定位）。
- **NGO-3**：不支持 **Bundle（插件包）** 与 serverless/远端运行时插件的离线化（单独评估，见风险 R6）。
- **NGO-4**：不支持 Windows/macOS 作为**插件运行目标平台**（目标即 Linux Docker）；不支持非 3.12 的 daemon 镜像（给出版本矩阵与处置建议，见 §5.1）。
- **NGO-5**：不保证“模型类插件在运行时调用外部模型 API”的联网（那是业务行为；工具只管依赖安装）。

## 4. 功能需求（FR）

> 优先级：P0（本期必做） / P1（本期做，宽松） / P2（规划）。
> 每个 FR 含验收标准（AC），验收基于 §8 测试计划。

### FR-1 输入与来源解析　P0
- 支持输入：
  1. 本地 `.difypkg`（官方市场下载或第三方，**主场景**）；
  2. 插件源码目录（含 `manifest.yaml` + `main.py` + `requirements.txt` 或 `pyproject.toml`，可含 `uv.lock`）；
  3.（P1）Marketplace 直接拉取（`marketplace.dify.ai/api/v1/plugins/<org>/<name>/<version>/download`）与 GitHub Release 拉取。
- 解析并展示：插件唯一标识（org/name@version）、类型（tools/models/agent_strategy/extension…）、`manifest.meta.runner`（python 版本/entrypoint/arch）、依赖文件类型与内容。
- AC：对官方 webscraper difypkg 与源码目录两种输入均能输出正确元数据；对非法/损坏 zip 给出明确中文报错（非崩溃）。

### FR-2 依赖解析与精确锁定　P0
- 依据 `requirements.txt` 或 `pyproject.toml(+uv.lock)` 生成**精确锁定**的依赖清单（等价 `uv lock` / `uv export --format requirements-txt` 结果，含全部传递依赖、精确版本）。
- 识别并处理特例：
  - sdist-only（无目标 wheel）依赖 → 记录并**预构建** wheel 或明确报错（对应 issue #25356 场景）；
  - git/url 直引依赖 → 明确报错（离线不可行，给出处置建议）；
  - 版本约束为空/过宽 → 以锁定时解析结果回填精确 pin。
- 输出：锁定清单（requirements 形式）、依赖树概览（顶层级数统计）。
- AC：对官方 `webscraper`（beautifulsoup4/lxml 等传递依赖）锁定结果可在纯离线（`--no-index`）下被 uv/pip 完整复现安装。

### FR-3 依赖获取与 wheel 准备　P0
- 在打包容器内按**目标平台**下载 wheel：
  - 默认目标：`linux` + `python 3.12`；架构：`amd64`/`arm64` 双架构（等价 uv `--python-platform linux --python-version 3.12` / pip `--platform manylinux_2_17_{x86_64,aarch64} --python-version 312 --only-binary=:all:` 的组合语义）；
  - 记录每个 wheel 的来源 URL 与 SHA256 至报告（供应链可审计）；
  - 对缺失 wheel 的 sdist-only 包：尝试用目标环境构建 wheel（build isolation 同目标 python/架构）。
- AC：能产出双架构完整闭包；缺失依赖时报告缺失清单（名称/期望版本/原因），退出码非 0。

### FR-4 包内改造（注入离线安装钩子）　P0
在插件源码根目录内：
- 注入 `wheels/` 目录（wheel 全集，按 PEP425 标签，双架构并存由安装端自动选择）；
- 若存在 `pyproject.toml`：写入/合并 `[tool.uv]` → `no-index = true`、`find-links = ["./wheels"]`（保留原配置项，冲突以离线配置为准并告警）；同步保留锁定文件；
- 若以 `requirements.txt` 为安装依据：在文件**首行**注入 `--no-index --find-links=./wheels/`（保留原始约束行或替换为锁定行，策略可配置：`preserve`/`lock`）；
- 处理 `.gitignore`/`.difyignore` 中 `wheels/` 与相关条目（打包时避免遗漏/或按官方 CLI 行为排除）。
- 不修改插件业务代码与 manifest 内容（除非显式 `--rewrite-version` 等，见 FR-8/FR-9）。
- AC：产物解压后，daemon 环境初始化路径可被验证为“纯本地解析”（单元/集成测试断言：`uv sync --offline` 或 `uv pip install --no-index -r requirements.txt` 在无网容器内成功）。

### FR-5 规范重打包与（可选）签名　P0
- 复用官方 `dify-plugin-<os>-<arch>` CLI（daemon 同版本发布物，Docker 镜像内置 linux 版本）执行最终打包，保证包结构与官方一致；
- 提供**可选**自签：生成组织 RSA 密钥对、对产物签名并写入 zip 注释 + `.verification.dify.json`（对应 daemon 第三方验签配置）；
- 输出命名与内容清单（原始元数据 + 改造记录 + 校验和）。
- AC：产物可被 plugin_daemon 0.6.10 解码（manifest/readme/assets/icon 检查通过）；`FORCE_VERIFYING_SIGNATURE=false` 场景直接可装；自签场景配合 §7 第三方公钥可装。

### FR-6 双架构产物策略　P0
- 默认：**单包双架构**（wheels 目录含 amd64+aarch64 全集，uv/pip 依 tag 自动选择）；
- 提供 `--arch amd64|arm64|both`（默认 both）；
- 产物信息/报告标注架构范围与 python 版本。
- AC：对含二进制 wheel 的插件（如 lxml），单包在 amd64 与 arm64 两套（模拟）目标上分别安装成功。

### FR-7 结果校验与报告　P0
- 结构自检：zip 可读、manifest 解析、必需文件存在、无路径穿越（`../`）、无遗漏 wheels；
- 完整性核对：锁定的每个包在 `wheels/` 中存在且可被目标 python/架构接受（tag 匹配检查）、无重复名冲突；
- 输出：`report.json`（元数据、锁定清单、wheel 清单+sha256、改造 diff、校验结论）+ 人类可读摘要；
- **可选在线试装验证**（P1，CI）：起 `plugin_daemon` 离线容器做真实安装冒烟。
- AC：报告覆盖上述项；失败即非 0 退出且给出可操作信息。

### FR-8 目标端部署支持　P0
- 生成随包部署说明（`DEPLOY-NOTES.txt`/README 章节），覆盖两种安全策略：
  1. 快速路径：目标端 `.env` 设 `FORCE_VERIFYING_SIGNATURE=false`（说明风险）；
  2. 安全路径：工具 `keygen` 生成组织密钥 → 目标 daemon 挂载公钥并设 `THIRD_PARTY_SIGNATURE_VERIFICATION_ENABLED=true` + `THIRD_PARTY_SIGNATURE_VERIFICATION_PUBLIC_KEYS=...`（需额外挂载卷），产物经自签后安装；
  3. 尺寸项：`PLUGIN_MAX_PACKAGE_SIZE`（默认 52428800 字节，含**解压后**总大小限制）与 `NGINX_CLIENT_MAX_BODY_SIZE` 调大建议值（500M 级）及生效方式（`docker compose up -d` 重建 plugin_daemon/nginx）。
- AC：文档给出的 .env 改动与官方 docker-compose 变量名完全一致（已核对）。

### FR-9 CLI 界面与工程约束　P0
- Docker 优先：主命令 `dify-offline-repack` 自检 docker；在 `python:3.12` 镜像内执行构建（联网依赖下载发生在打包容器内）；产物写回宿主机挂载目录。
- 子命令建议：
  - `inspect <pkg|dir>`：元数据/依赖预览（不联网）
  - `repack [--src-type local|dir] <input> -o <outdir> [--arch both] [--py 3.12] [--index <pypi镜像>] [--lock|--preserve] [--no-verify]`
  - `keygen` / `sign`：密钥生成与自签
  - `batch <manifest.jsonl|dir-of-difypkg>`：批量模式（P0 轻量支持：目录下多个 difypkg 依次处理）
  - `verify <offline.difypkg>`：仅离线结构/闭包静态校验
- 规范：退出码（0 成功 / 1 失败 / 2 参数错 / 3 环境不满足）、日志分级、`--dry-run`、进度输出到 stderr、产物/报告到 stdout 路径。
- AC：Windows 宿主机一条命令跑通 webscraper 端到端（见 §8）。

### FR-10 批量与清单　P1
- 输入多个 difypkg（目录或清单文件），逐个重打包；单包失败不中断整体；汇总 `summary.csv/md`。
- AC：10 个官方工具插件混合成功/失败场景下输出正确汇总与逐项原因。

### FR-11 错误处理与诊断　P1
- 把离线安装常见失败（网络不可达/索引超时、wheel 缺失、python/架构不匹配、签名被拒、超包体限制、git 依赖、sdist 构建失败）归类为**带修复建议的中文错误码**（见 §7 附录错误码草案），工具端与部署端一致引用。
- AC：针对 25356（缺 wheel）与 30725（pip 环境缺失表象）给出对应诊断建议并可复现提示。

## 5. 范围约束与兼容矩阵

### 5.1 目标平台矩阵

| 目标环境 | Dify 版本 | plugin_daemon 镜像 | python | 安装机制 | 支持 |
|---|---|---|---|---|---|
| 主目标 | 1.16 / 1.17（社区 Docker） | 0.6.10-local | 3.12 | uv venv + uv sync/pip | **本期支持（默认）** |
| 兼容观察 | 2.0.0-beta.2 | 同 0.6.x | 3.12 | 同上 | 支持（同机制），按 beta 提示 |
| 观察 | 1.9 ~ 1.15 | 旧版 daemon（0.1.x~0.5.x） | 不定 | pip/venv 流程差异 | 待单列验证；工具保留“离线钩子”兼容设计（requirements 首行对 pip 同样生效；pyproject 注入依赖 daemon 支持 uv） |
| 不支持 | ≤ 1.8 等更早/深度魔改环境 | — | — | — | 文档标注，建议镜像方案 |

### 5.2 插件范围
- 支持：官方 dify-plugins（langgenius）及第三方工具的常规类型——**工具（tools）、模型（models）、Agent 策略、扩展（extension）、数据源**中“本地 python 运行时”且以 requirements/pyproject 声明依赖者。
- 不支持/需评估：**Bundle**（多插件容器，见 R6）；serverless/远端运行时；含 C 扩展但目标无 wheel 且无法离线构建者。

### 5.3 网络假设
- 打包机/CI：可访问 PyPI（或指定镜像，如 `--index`）；
- 目标机：零外网（也不依赖内网 pip 源）。

### 5.4 包体限制（事实约束）
- daemon 侧 `MAX_PLUGIN_PACKAGE_SIZE`（compose 默认 `52428800`）同时约束上传体与**解压后总大小**（`ZipDecoderWithSizeLimit` 校验 UncompressedSize 总和）；
- 前端 `NGINX_CLIENT_MAX_BODY_SIZE` 默认较小。
- 因此携带 wheels 的大插件需目标端放大（FR-8.3），工具应**预告产物压缩/解压后大小并预警超限**。

### 5.5 签名与安全策略
见 FR-8 两路径。默认推荐 **安全路径（自签 + 第三方公钥）**；快速路径作为兼容兜底并提示风险。

## 6. 非功能需求（NFR）

- **正确性**：产物通过 §8 测试计划（尤其真离线安装冒烟）方可发布版本。
- **可复现性**：同一输入 + 参数 → 依赖锁定与 wheel 集确定（记录 uv/pip 版本、锁文件 sha256）。
- **可移植性**：CLI 面向 Windows/macOS/Linux 宿主机（内部统一 Docker 执行）；产物面向 Linux amd64/arm64。
- **安全**：工具不在宿主机执行插件代码（解析仅静态/沙箱容器内）；记录供应链 sha256；避免路径穿越写盘。
- **性能**：单个普通工具插件打包 ≤ 3~5 分钟（含下载）；增量缓存 wheels（可选 P2）。
- **文档语言**：中文为主（README/报告可双语）。
- **错误可诊断性**：见 FR-11。

## 7. 需求验收总则与错误码草案

**通过条件**（对 webscraper 等 ≥5 个代表性官方插件）：
1. 离线容器（断网模拟）内 `plugin_daemon` 安装离线包成功、插件可正常发现；
2. amd64 与 arm64 两目标均通过（或显式产物说明）；
3. 报告与部署说明与产物一致、可直接照做。

**错误码草案**（ENV- 打包端 / INST- 安装端）：

| 码 | 场景 | 处置 |
|---|---|---|
| ENV-1001 | 依赖含 git/url 引用 | 提示锁定到 wheel 或联系插件作者 |
| ENV-1002 | 某依赖无目标 wheel 且构建失败 | 给出缺失包名/约束/构建日志摘要 |
| ENV-1003 | 双架构闭包不完整 | 提示降级单架构或补充镜像源 |
| INST-2001 | 目标端验签拒绝 | 部署说明第 1/2 路径 |
| INST-2002 | 超包体限制 | 调大 PLUGIN_MAX_PACKAGE_SIZE / NGINX_CLIENT_MAX_BODY_SIZE |
| INST-2003 | 安装仍联网失败 | 检查是否旧版 daemon / 依赖清单泄漏索引 URL |
